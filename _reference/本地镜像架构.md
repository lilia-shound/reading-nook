# 本地镜像：为什么本机服务突然变快了

给云端姜去看的 —— **2026-10-23**。

## 先说结论

仓库还是唯一事实来源，**铁律一条没松**（写之前永远先 GET 远端最新那份 `.enc`，在那份上改，再 PUT）。
变的只有**读**的路：以前读一次数据就是一次 GitHub 网络往返（实测 1.7 秒），翻一页要读好几个文件 → **整页 20 秒以上**，本机那版基本没法看。
现在读走**本地镜像**，后台每 20 秒跟远端对齐一次。

| | 以前 | 现在 |
|---|---|---|
| 读一个文件 | 1.7 秒 | 0.03~0.2 秒 |
| 打开一章（好几个文件） | 20 秒+ | 0.4 秒 |
| 首页 | 22.8 秒 | 0.43 秒 |

## 对你（云端姜去）有什么影响

**几乎没有** —— 镜像是**默认关着的**，只有 `server.js` 会显式打开。

- 你用 `tools/gh-store.js` 读写，**不走镜像**，每次都问远端 → 你拿到的永远是「此刻最新」的那份。
- 为什么这样分：镜像换来的是速度，代价是**最多落后 20 秒**。你回批注要基于她刚划的那一条，不能拿旧的。

如果你以后也想在自己那台机器上跑 `node server.js`，镜像会自动开（`server.js` 里 `gh.enableMirror()`）。

## 新增了什么文件

- `lib/vault-node.js` —— **必须和 `lib/ghbackend.js` 一起拉**，少了它你的 `gh-store.js` 会直接崩（`ghbackend.js` 要 `require` 它）。
  它是加密的 Node 版（同步），格式跟 `public/vault.js` **一模一样**（那个是唯一一份定义）。
  以前加解密是丢进 `execFileSync` 子进程跑的 —— 光 spawn 一次 node 就要 **578 毫秒**；现在进程内同步做 + 密钥缓存，**0.03 毫秒**。
  有 `test/check_vault_node.js` 盯着：两个方向互解，跑偏了当场发现。

## 两个坑（都踩过了，记一下）

1. **同步子进程不能没有超时**。
   `execFileSync` 等子进程，子进程里 `https.request` 又不设超时 → 卡在 DNS 解析里就永远不退出 → **父进程整个事件循环被冻住**，连静态页都不回（表现像「服务挂了」）。
   现在三层保险：子进程里自己实现带超时的 `lookup`（管 DNS）→ `r.setTimeout`（管等响应）→ 兜底总时长（管卡在别的地方）；父进程 `execFileSync` 再加一道 `timeout` + `killSignal`。

2. **写路径绝对不能吃「旧数据兜底」**。
   读网络断了可以用镜像里旧的那份（宁可旧也别让她打不开书）；
   但写要是拿旧数据当基底，就会把云端那位刚写的回应冲掉（GitHub 的 PUT 是 last-write-wins）。
   所以：读可以兜底，**写必须硬失败**。

## 合并语义没变

`updateFileSync` 依然是「读远端最新那份 → 合并 → PUT 回去」，**不读镜像**。
409 / 422 也是**整轮重来**（重新读远端 + 重新合并），不是只换 sha。
你自己写的那份，镜像是**写完立刻回填**的 —— 她马上就能看到。
